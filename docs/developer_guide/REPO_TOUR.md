# Repository Tour

This page gives new contributors a quick map of the repository and a concrete reading path. It stays focused on where code and docs live, not on subsystem internals.

## Top-level folders contributors should know

- `kedehub/`: main application code. This is where the CLI entrypoint, orchestration, Git analysis code, configuration handling, and service-layer calls live.
- `kedehub_client/`: client code for talking to the KEDEHub server, including auth, API client setup, and generated API bindings.
- `tests/`: test suite. It includes local unit-style tests and broader integration-style tests, so not every test is the right first check for a new contributor.
- `docs/`: user-facing and contributor-facing documentation. The developer guide lives under `docs/developer_guide/`.
- `dockerize/`: Docker build and runtime assets, plus Docker-specific usage notes.
- `build/`: generated build artifacts from packaging or PyInstaller work. Do not edit files here manually.
- `plans/`: implementation plans used to stage documentation and development work.

Generated and local-environment folders are also present in this repository from time to time:

- `venv311/` or `.venv/`: local virtual environments.
- `kedehub.egg-info/`: packaging metadata generated by install/build workflows.
- `__pycache__/`: Python bytecode caches inside package directories.

Treat these as local or generated state, not as primary contributor entrypoints.

## Recommended reading path

Use this order when you are getting oriented:

1. Start with [README.md](../../README.md) for the project-level overview and the user-facing context.
2. Continue with [docs/developer_guide/README.md](./README.md) for the contributor workflow and the rest of this guide.
3. Read [kedehub/__main__.py](../../kedehub/__main__.py) to see how commands are defined and dispatched.
4. Read [kedehub/kedegit.py](../../kedehub/kedegit.py) to see the main repository-processing flow.
5. Scan [kedehub/services/](../../kedehub/services/) next to see how the core workflow persists data and talks to the server-facing layer.
6. Finish with [kedehub_client/](../../kedehub_client/), starting from [kedehub_client/__init__.py](../../kedehub_client/__init__.py), if you need to follow HTTP client creation, auth, and API access.

That path is enough to understand how a CLI command turns into repository processing and server calls without taking a full architecture detour yet.

## What to open first inside the main code folders

- In [kedehub/](../../kedehub/), start with [__main__.py](../../kedehub/__main__.py) and [kedegit.py](../../kedehub/kedegit.py) before exploring deeper modules.
- In [kedehub/services/](../../kedehub/services/), expect thin service-oriented modules grouped by concern such as authors, commits, projects, repositories, templates, and ranking.
- In [kedehub_client/](../../kedehub_client/), start with [__init__.py](../../kedehub_client/__init__.py), then [api_client.py](../../kedehub_client/api_client.py) and [auth.py](../../kedehub_client/auth.py) if you need to follow request setup.
- In [tests/](../../tests/), prefer targeted local tests first. Use the [onboarding guide](./ONBOARDING.md) before running the broader suite.

## Contributor guidance

If you are making your first change, stay out of generated outputs and local environments unless the task is explicitly about build tooling:

- do not edit `build/` manually
- do not treat `venv311/`, `.venv/`, or `__pycache__/` as source
- do not assume every file under `tests/` is safe to run offline without checking the onboarding guidance first
